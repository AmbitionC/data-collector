# Side Panel 交互链路与错误场景设计

侧栏是这个工具唯一的人机界面。它同时被两条链路驱动（用户点击的即时反馈、轮询本机状态的推导结果），
历史上因为两条链路没有优先级约定，出现过「错误屏被 1 秒后的轮询覆盖成『已完成』」这类事故。
本文定义状态、优先级和每一个错误场景的出路，改动交互前先改本文。

## 一、唯一真相源与优先级

### 1. 状态只有三个来源，且优先级固定

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1（最高） | **本地粘性错误** | 用户点击后立刻失败、且失败信息没能写进 storage 的情况（如“找不到可采集的标签页”）。**只有用户动作能清除**，轮询不得覆盖。 |
| 2 | **连接状态** `bridgeStatus` | 没连上本机服务时，页面级状态没有意义，一律先解决连接。 |
| 3 | **当前页面的最新事件** | 单页任务记录（`lastJob*`）或批量记录（`batch`），二者互斥（见下）。 |
| 4（最低） | **页面可采性** | `ready` / `unsupported`。 |

### 2. 单页任务与批量记录互斥

同一个页面不可能同时在跑“保存这一页”和“批量保存”：

- 发起单页保存时清除 `batch`；
- 发起批量保存时清除 `lastJob*`。

因此渲染时不需要比较两者谁更新，谁存在就是谁。

### 3. 事件归属于页面

`lastJobUrl` / `batch.url` 必须等于当前活动标签页的 URL，否则忽略该记录。
换页面 = 换上下文，不拿上一页的结果打扰用户。

### 4. 终态不会自动消失

`saved` / `failed` / 批量的任何终态，都停留到用户点了按钮（重试 / 完成 / 换页面）为止。
**任何情况下都不允许出现「错误屏一闪而过、自动推进到下一屏」。**

## 二、状态机

```
                      ┌──────────┐
                      │ loading  │  读取本机状态
                      └────┬─────┘
                           v
        ┌──────────── bridgeStatus ────────────┐
        │                                      │
   connecting                            connected
        │                                      │
        v                                      v
 bridge_unavailable                   ┌── 当前页事件 ──┐
 replaced                             │               │
 identity_error                    有记录          无记录
                                      │               │
                        ┌─────────────┴───┐           v
                        │                 │      ready / unsupported
                   单页任务            批量记录
                        │                 │
        ┌───────────────┼──────┐    ┌─────┴──────────────────────┐
        v               v      v    v                            v
   collecting        saved  failed / needs_attention      batch.phase（见三）
```

### 页面模式：单页 vs 列表

`ready` 分两种形态，由 `isListPage(url)`（shared 的唯一判据）决定：

| 形态 | 主按钮 | 走的链路 |
| --- | --- | --- |
| 单页 | 保存这一页 | `capture.current` → 单页任务记录 |
| 列表 | 批量保存本页帖子 | `capture.list` → 批量记录 |

## 三、批量记录的终态（本次事故的核心）

**「结束」不等于「完成」。** 批量记录带一个显式 `phase`，每个终态有各自的文案和出路：

| phase | 何时 | 标题 | 出路 |
| --- | --- | --- | --- |
| `running` | 进行中 | 正在批量归档 | 显示实时计数 + **停止**按钮 |
| `done` | 跑到没有新内容，且至少入库 1 条 | 本轮批量归档完成 | 继续采下一批 / 完成 |
| `capped` | 达到单次上限（60 条 / 12 轮） | 已达单次上限，本页可能还有更多 | 继续采下一批 / 完成 |
| `stopped` | 用户主动停止 | 已停止，本轮入库 N 条 | 继续采下一批 / 完成 |
| `empty` | 本页一条帖子都没识别到 | 本页没有找到可采集的帖子 | 重试（并提示可能还没加载完） |
| `skipped_all` | 识别到帖子但全部拿不到各自链接 | N 条都无法确定各自的链接 | 重试 + **复制诊断信息** |
| `failed` | 中途异常终止 | 批量归档中断 | 显示原因 + 针对性按钮（见四） |

`done` / `capped` / `stopped` 才显示成功语气；`empty` / `skipped_all` / `failed` 一律显示为需要处理，
并且**如实带上已入库条数**（中断前采到的不能不认）。

## 四、错误场景矩阵

每一条都必须有：明确的原因文案、明确的下一步按钮、不会被自动覆盖。

| # | 场景 | 判据 | 文案要点 | 出路按钮 |
| --- | --- | --- | --- | --- |
| E1 | 页面脚本未就绪 | 消息发不到内容脚本（`Receiving end does not exist`） | 插件重载后，之前打开的标签页需要重新加载一次 | **刷新页面并重试**（扩展自己 reload 标签页再跑，用户不必看懂提示） |
| E2 | 未登录 | 提取器返回 `AUTH_REQUIRED` | 请先在同一浏览器登录知识星球 | 保留页面 + 重试 |
| E3 | 本页没有帖子 | 首轮 `total === 0` | 可能还没加载完，或当前不是帖子列表 | 重试 |
| E4 | 全部拿不到链接 | `collected === 0 && skipped > 0` | 每条必须带自己的 `/topic/` 地址才能分别入库；这是页面结构适配问题 | 重试 + **复制诊断信息**（把首条帖子的链接/属性结构复制到剪贴板，直接贴给我改适配） |
| E5 | 本机服务中途断开 | 建任务时 fetch 失败 | 已入库 N 条；本机服务无响应 | 重试（续采，已入库的不会重复） |
| E6 | 个别帖子失败 | 单条建任务失败 | 不中断整批，计入「失败」，结束时汇总 | —（随终态一起展示） |
| E7 | 用户主动停止 | 点了停止 | 已停止，本轮入库 N 条 | 继续 / 完成 |
| E8 | 后台进程被回收 | 进度停更超过 90 秒仍标 running | 浏览器回收了后台进程，本批已中断 | 重试（续采） |
| E9 | 达到上限 | 60 条 / 12 轮 | 已达单次上限，本页可能还有更多 | 继续采下一批 |
| E10 | 找不到可采集标签页 | 查询活动标签页失败 | —— | 走**本地粘性错误**（优先级 1），不写批量记录 |

### 去重与续采

「继续采下一批」「重试」都是**续采**语义：已入库的帖子在页面上已被打标记收起，
且批量内部按规范 URL 去重，因此重复点不会产生重复条目。

## 五、不允许的做法（回归清单）

写代码或改交互时，下面每一条都要能答“否”：

1. 错误信息会不会被下一次轮询覆盖？
2. 有没有把「异常中止」渲染成「完成」？
3. 有没有在 0 条入库时显示成功语气？
4. 有没有让用户去看懂一段提示、再自己去做一件插件能自己做的事（如手动 F5）？
5. 运行中的长任务有没有给用户中止的办法？
6. 有没有静默截断（到达上限却不说）？

对应的测试在 `tests/unit/sidepanel.test.ts` 与 `tests/unit/background.test.ts`，
端到端回归在 `tests/e2e/extension.test.ts`。
