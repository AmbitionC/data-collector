# Side Panel 交互链路与错误场景设计

侧栏是这个工具唯一的人机界面。它同时被两条链路驱动（用户点击的即时反馈、轮询本机状态的推导结果），
历史上因为两条链路没有优先级约定，出现过「错误屏被 1 秒后的轮询覆盖成『已完成』」这类事故。
本文定义状态、优先级和每一个错误场景的出路，改动交互前先改本文。

## 一、唯一真相源与优先级

### 1. 状态只有三个来源，且优先级固定

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1（最高） | **本地粘性错误** | 用户点击后立刻失败、且失败信息没能写进 storage 的情况（如“找不到可采集的标签页”）。**只有用户动作能清除**，轮询不得覆盖。 |
| 2 | **连接状态** `bridgeStatus` | 没连上本机服务时，页面级状态没有意义，一律先解决连接。 |
| 3 | **当前页面的最新事件** | 单页任务记录（`lastJob*`）或批量记录（`batch`），二者互斥（见下）。 |
| 4（最低） | **页面可采性** | `ready` / `unsupported`。 |

### 2. 单页任务与批量记录互斥

同一个页面不可能同时在跑“保存这一页”和“批量保存”：

- 发起单页保存时清除 `batch`；
- 发起批量保存时清除 `lastJob*`。

因此渲染时不需要比较两者谁更新，谁存在就是谁。

### 3. 事件归属于页面

`lastJobUrl` / `batch.url` 必须等于当前活动标签页的 URL，否则忽略该记录。
换页面 = 换上下文，不拿上一页的结果打扰用户。

### 4. 终态不会自动消失

`saved` / `failed` / 批量的任何终态，都停留到用户点了按钮（重试 / 完成 / 换页面）为止。
**任何情况下都不允许出现「错误屏一闪而过、自动推进到下一屏」。**

## 二、状态机

```
                      ┌──────────┐
                      │ loading  │  读取本机状态
                      └────┬─────┘
                           v
        ┌──────────── bridgeStatus ────────────┐
        │                                      │
   connecting                            connected
        │                                      │
        v                                      v
 bridge_unavailable                   ┌── 当前页事件 ──┐
 replaced                             │               │
 identity_error                    有记录          无记录
                                      │               │
                        ┌─────────────┴───┐           v
                        │                 │      ready / unsupported
                   单页任务            批量记录
                        │                 │
        ┌───────────────┼──────┐    ┌─────┴──────────────────────┐
        v               v      v    v                            v
   collecting        saved  failed / needs_attention      batch.phase（见三）
```

### 页面模式：单页 vs 列表

`ready` 分两种形态，由 `isListPage(url)`（shared 的唯一判据）决定：

| 形态 | 主按钮 | 走的链路 |
| --- | --- | --- |
| 单页 | 保存这一页 | `capture.current` → 单页任务记录 |
| 列表 | 批量保存本页帖子 | `capture.list` → 批量记录 |

## 三、批量记录的终态（本次事故的核心）

**「结束」不等于「完成」。** 批量记录带一个显式 `phase`，每个终态有各自的文案和出路：

| phase | 何时 | 标题 | 出路 |
| --- | --- | --- | --- |
| `running` | 进行中 | 正在批量归档 | 显示实时计数 + **停止**按钮 |
| `done` | 跑到没有新内容，且至少入库 1 条 | 本轮批量归档完成 | 继续采下一批 / 完成 |
| `capped` | 达到单次上限（60 条 / 12 轮） | 已达单次上限，本页可能还有更多 | 继续采下一批 / 完成 |
| `stopped` | 用户主动停止 | 已停止，本轮入库 N 条 | 继续采下一批 / 完成 |
| `empty` | 本页一条帖子都没识别到 | 本页没有找到可采集的帖子 | 重试（并提示可能还没加载完） |
| `skipped_all` | 识别到帖子但全部拿不到各自链接 | N 条都无法确定各自的链接 | 重试 + **复制诊断信息** |
| `failed` | 中途异常终止 | 批量归档中断 | 显示原因 + 针对性按钮（见四） |

`done` / `capped` / `stopped` 才显示成功语气；`empty` / `skipped_all` / `failed` 一律显示为需要处理，
并且**如实带上已入库条数**（中断前采到的不能不认）。

## 四、错误场景矩阵

每一条都必须有：明确的原因文案、明确的下一步按钮、不会被自动覆盖。

| # | 场景 | 判据 | 文案要点 | 出路按钮 |
| --- | --- | --- | --- | --- |
| E1 | 页面脚本未就绪 | 消息发不到内容脚本（`Receiving end does not exist`） | 插件更新后，已打开的标签页里没有内容脚本 | **扩展自动注入内容脚本后重试**，用户通常察觉不到；注入也失败才报错 |
| E2 | 未登录 | 提取器返回 `AUTH_REQUIRED` | 请先在同一浏览器登录知识星球 | 保留页面 + 重试 |
| E3 | 本页没有帖子 | 首轮 `total === 0` | 可能还没加载完，或当前不是帖子列表 | 重试 |
| E4 | 全部拿不到链接 | `collected === 0 && skipped > 0` | 区分两种：**还没截到接口响应**（`TOPIC_INDEX_EMPTY`，滚动一屏或切一次分类即可）／**截到了但对不上号**（`TOPIC_INDEX_MISMATCH`，需要修适配） | 重试 + **复制诊断信息** |
| E5 | 本机服务中途断开 | 建任务时 fetch 失败 | 已入库 N 条；本机服务无响应 | 重试（续采，已入库的不会重复） |
| E6 | 个别帖子失败 | 单条建任务失败 | 不中断整批，计入「失败」，结束时汇总 | —（随终态一起展示） |
| E7 | 用户主动停止 | 点了停止 | 已停止，本轮入库 N 条 | 继续 / 完成 |
| E8 | 后台进程被回收 | 进度停更超过 90 秒仍标 running | 浏览器回收了后台进程，本批已中断 | 重试（续采） |
| E9 | 达到上限 | 60 条 / 12 轮 | 已达单次上限，本页可能还有更多 | 继续采下一批 |
| E10 | 找不到可采集标签页 | 查询活动标签页失败 | —— | 走**本地粘性错误**（优先级 1），不写批量记录 |

**粘性错误 vs 批量记录，谁说了算**：后台**明确回报**的失败（中文原因，如 E10）粘在屏上，
谁都不许覆盖。但「和后台失联」是另一回事——端口关闭 / 上下文失效抛出的是浏览器的原生
英文报错，只说明这条消息回不来了，批量本身可能已经跑了一半；这时**批量记录才是真相源**
（含 E8 判定）。两者混为一谈的话，原生英文报错会一直顶在最前面，E8 那块屏永远显示不出来。

### 「一个帖子号都没截到」必须分清是哪一种

`已捕获帖子号 0 个` 有三种完全不同的成因，只报这个数字分不出来，用户照着一句
放之四海皆准的建议去做也解决不了（实测绕了好几轮）。主世界钩子因此上报运行统计
（`HookStats`），面板据此给出**唯一对得上的那句话**：

| 统计 | 成因 | 说法 |
|---|---|---|
| `installed: false` | 钩子压根没跑 | 确认扩展已启用，**新开一个标签页**（不刷新本页） |
| `installed: true, observed: 0` | 钩子在跑，但页面这段时间一个请求都没发 | 把分类切走再切回来 |
| `jsonResponses > 0, withTopicId: 0` | 站点接口结构变了 | 复制完整报告给开发者 |

三种说法必须彼此不同，否则等于没区分（有测试盯着这一点）。

**但首选不是「告诉用户怎么做」，而是插件自己做掉**：第一轮若一个帖子号都没截到，
批量会**替用户切走分类再切回来**（唯一能不刷新页面就让站点重新请求的办法——刷新会把
「精华」退回「最新」），然后重跑这一轮。只做一次，且无论中途出什么岔子都必须切回原分类。
这一步是纯便利，失败绝不能把整批采集带下水。

统计应答的监听**必须无条件注册**，不能只在「这次真的打了补丁」时注册：扩展更新后页面里
留着的是老版本补丁，新注入的这份会跳过打补丁流程，若连监听也跳过，就会把「钩子其实在跑」
误报成「钩子没在运行」，把人引向完全错误的处置方向（实测踩过）。

### 绝不刷新用户的页面

**任何自愈都不许 reload 标签页。** 知识星球的分类（精华 / 最新 / 分组）是应用内状态，
不在 URL 里；刷新会退回默认的「最新」，于是用户在精华页发起的采集采成了别的内容。
内容脚本缺失一律用 `chrome.scripting.executeScript` 注入解决——注入不动页面状态。
同理，任何提示都不该写「请按 F5 刷新」。

**自愈要补的是两个脚本，不是一个**（清单见 `packages/extension/src/background/injection.ts`）：
内容脚本（隔离世界）+ 主世界帖子号钩子 `inject.js`。帖子号只存在于站点自己的接口响应里，
钩子不补，「已捕获帖子号」永远是 0 → 批量必然全部跳过，而面板还在让用户滚动页面——
钩子都不在，滚多久都等不到结果。这条曾让批量功能对所有「装扩展之前就打开的标签页」
彻底不可用，且从提示里完全看不出原因。补钩子之前那次接口响应已经错过，
因此 E5 的文案必须先说清这个成因，再给「切换分类重新请求」这个真能解决问题的动作。

### 绝不改变页面外观

处理过的帖子只打一个**不可见**的属性标记（`data-dc-collected`），下一轮据此跳过。
早先的实现顺手把它们 `display:none` 收起（想压缩页面高度好触发懒加载），
但用户要肉眼核对采到的内容对不对——把帖子藏起来是硬伤。加载下一批纯靠滚动到底
触发站点自己的懒加载。

- **重新发起一批**（ready 面板的按钮、或终态的「重试」）→ 先清掉全部标记，再从头采；
- **「继续采下一批」** → 保留标记，并且**先滚动加载下一页再提取**（本屏都处理过了，
  不先滚就只会得到「没有待采内容」）。

### 本轮明细（逐条核对）

批量是个多轮的长流程，只给三个数字不足以判断对错。终态下（只要看到过帖子）提供
「查看本轮明细」子页面：

- 逐条列出标题与状态（已入库 / 已跳过 / 失败），跳过和失败**必须带原因**；
- 顶部按状态筛选，每个筛选带条数；
- 点某一条 → 页面滚到它那儿并加边框高亮，节点已被站点回收时如实说「不在页面上了」；
- 可复制**整轮的完整报告**：批量记录 + 逐条结果 + 页面结构 + **主世界钩子的运行统计**；
- **点未入库的条目会把单条证据包复制到剪贴板**（`diagnosticsVersion: 4`）：构建版本、
  页面帖子数 vs 已截获帖子号数、这条的页面文本，以及最像的几条接口记录（**保留接口原文**）
  与最长共同片段长度。「为什么这条被跳过」必须能一键取证——只报一个总数根本定位不了，
  为此绕过好几轮。

### 去重与续采

「继续采下一批」是续采：已入库的帖子在页面上已被打了不可见标记，
且批量内部按规范 URL 去重，因此重复点不会产生重复条目。

## 四之二、同步是独立的一步

采集屏**不提供去向选择**：采集只落本机库，选了也不会生效，摆一个不起作用的控件比没有更糟。
ready 面板改为两句话——「保存去向：本机库（采集只落本地）」+「核对无误后可在『已入库』里同步到 X」。

「已入库」页承担第 2、3 步：

- 两排筛选（来源 / 同步状态），每行一个同步状态徽标——「该同步哪些」必须一眼可见；
- 逐条「同步」与批量「同步未同步的 N 条」；同步中按钮禁用并显示进行中；
- 同步结果**逐条点名**：失败了是哪一条、为什么，绝不只给个总数；
- 全部已同步时批量按钮禁用并写明「全部已同步」，而不是留一颗点了没反应的按钮。

## 五、不允许的做法（回归清单）

写代码或改交互时，下面每一条都要能答“否”：

1. 错误信息会不会被下一次轮询覆盖？
2. 有没有把「异常中止」渲染成「完成」？
3. 有没有在 0 条入库时显示成功语气？
4. 有没有让用户去看懂一段提示、再自己去做一件插件能自己做的事？
4.5 有没有为了自愈而刷新用户的页面、丢掉他所在的站内分类？有没有留下没还原的 DOM 改动？
5. 运行中的长任务有没有给用户中止的办法？
6. 有没有静默截断（到达上限却不说）？
7. 结果屏说的「去向」是不是写死的？默认可能同时写多处、用户也可能只选一处，
   必须报出**这一篇实际写成功的那几处**，不许一律写「本地知识库」。
8. 有没有把浏览器的原生英文报错直接摆给用户看？
9. 有没有在采集阶段就把内容投递出去？（必须先落本机库，同步是用户显式发起的第二步）
10. 同步失败有没有点名是哪一条、为什么？只报总数等于没报。

对应的测试在 `tests/unit/sidepanel.test.ts` 与 `tests/unit/background.test.ts`，
端到端回归在 `tests/e2e/extension.test.ts`。
