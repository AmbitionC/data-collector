# 牛客面经交付提速与公开来源模块下线设计

## 1. 背景与目标

当前 `nowcoder-agent-market` 已能从牛客发现近期大厂 Agent 研发面经、通过 Edge 扩展读取详情、保存原始证据、同步到 `front-end-journey-resource`，再生成公开面经、扩充知识点并按唯一问题簇累加热度。

现有流程主要有三个问题：

1. 扩展把所有远程详情任务放进同一个严格串行队列，详情页等待占采集时间的绝大部分；
2. 固定计划只从搜索首屏组成最多 12 条、每家公司最多 4 条的详情池，随着历史 URL 增加，单轮越来越难补足 10 篇合格内容；
3. 计划自动接受结果与后续人工跨批次挑选发生偏离，无法准确解释一篇公开面经来自哪个精确批次，也无法完整比较各阶段耗时。

本次目标是在不降低真实性、完整性、去重、知识加权和设备安全标准的前提下：

- 通过受控双并发缩短详情采集时间；
- 通过分轮补足稳定获得最多 10 篇新的合格大厂 Agent 面经；
- 让一次交付只消费可核对的精确运行清单；
- 使用同一套指标比较优化前后的时间和质量；
- 从公开面经文章中下线独立的“来源”模块，但内部继续完整保存来源 URL、证据等级、内容指纹、问题簇和处置历史。

## 2. 已确认的基线

上一轮有效采集由 5 个批次组成：35 个牛客详情任务的活跃批次时间合计约 1002.7 秒，最终发布 10 篇。搜索发现每轮约 1.4–5.4 秒，最终选择不足 0.4 秒，详情采集是主要耗时。

上一批 10 篇公开面经的基线为：

- 证据等级 A 级 5 篇、B 级 5 篇；
- 字节 3 篇、腾讯 4 篇、蚂蚁 3 篇、阿里 0 篇；
- 10 个独立问题簇；
- 平均约 974 个汉字、8.7 个问题章节、3.2 个知识点链接；
- 0 个公开重复簇。

历史记录没有精确记录人工编写各阶段耗时，因此新旧时间比较以可复原的活跃采集时间为主要基线；新的运行会额外记录整理、验证和发布阶段，不能把历史整场开发会话时间误作采集耗时。

## 3. 范围与非目标

### 3.1 本次范围

- Data Collector 扩展的远程详情任务调度；
- Bridge 的牛客候选发现、失败重试边界和目标补足批次；
- 精确批次/运行清单和性能、质量基准报告；
- `front-end-journey-resource` 新旧公开面经中的独立 `## 来源` 模块；
- 新一批 10 篇面经、对应知识点更新、唯一问题簇热度和线上发布。

### 3.2 非目标

- 不接入牛客未公开或未经授权的内部接口；
- 不扩大扩展域名权限；
- 不把并发提升到 3 个或更多标签页；
- 不修改日常知识星球计划；
- 不在正常内容交付中修改或部署 `fe-journey-faas`；
- 不删除本机原始证据、候选索引或 `.codex/interview-source-history.json`；
- 不降低 30 天时效、A/B 证据、最少问题数、隐私清理或内容完整性标准。

## 4. 总体架构

优化后仍保持现有边界：

1. Bridge 使用公开搜索页发现候选并创建固定计划任务；
2. Edge 扩展使用登录态打开牛客详情并提取正文；
3. Bridge 保存本机证据并按真实性规则筛选；
4. 精确运行清单进入资源仓库收件箱；
5. 资源仓库 Skill 负责编辑、问题簇去重、知识点更新和发布；
6. GitHub Actions 同步线上内容。

变化集中在三个小组件：

- `RemoteJobScheduler`：最多两个后台详情任务，交互任务优先；
- `NowcoderTargetFill`：按小轮次补候选，直到得到 10 条合格来源或达到安全预算；
- `DeliveryBenchmark`：保存阶段时间、候选处置和质量结果，不保存新的原文副本。

## 5. 受控双并发

### 5.1 调度规则

- 所有 Data Collector 创建的远程详情标签页共享容量为 2 的调度器；
- 用户主动单页采集进入高优先级队列，固定计划任务进入普通队列；
- 已经开始的任务不强制中断，高优先级任务在下一个空槽立即执行；
- 知识星球三视图计划和其关联长文逻辑不改为并发；
- 每个详情任务继续使用现有的页面完成等待、内容脚本自愈和最多 5 轮正文提取重试。

### 5.2 质量与资源保护

- 牛客批次中仅 `CONTENT_EMPTY`、`UNSUPPORTED_LAYOUT`、标签页暂时错误属于可恢复失败；
- 首轮并发结束后，可恢复失败最多进入一次单槽串行兜底；
- `AUTH_REQUIRED`、不支持 URL、真实性不足和永久布局错误不盲目重试；
- 每个任务在 `finally` 中关闭自己创建的标签页；
- 扩展启动时继续清理上次异常退出遗留的 owned tabs；
- 用户原有标签页从不登记为 owned tab，因此不会被关闭；
- 验收时峰值 owned remote tabs 必须不超过 2，结束后必须为 0。

## 6. 候选发现与目标补足

### 6.1 去重状态

候选 URL 分为三类：

- 已保存、已发布或已归并：永久跳过；
- 明确因证据不足、过期、推广、非目标公司而拒绝：永久跳过，除非原 URL 内容指纹发生变化；
- `failed` 或 `needs_attention` 且从未成功保存：冷却后允许重试一次。

是否公开发布最终仍由资源仓库的永久来源历史决定。可恢复采集不会让同一 URL 或同一问题簇重复发布，也不会重复增加知识热度。

### 6.2 公开发现策略

- 保留现有腾讯、字节、阿里、蚂蚁定向查询；
- 增加少量岗位与主题明确的公开查询变体，例如 Agent 开发、AI 应用、Code Agent、RAG/MCP，不使用模糊的纯公司热帖查询；
- 规范化 URL 后再与本机任务、候选索引和永久历史去重；
- 候选排序依次考虑发布时间、公司多样性、Agent 研发相关度和是否为可恢复失败；
- 公司上限从阻塞规则改成多样性优先：有足够合格候选时尽量覆盖四家公司，某家公司暂无合格来源时不得用低质量内容凑数。

### 6.3 分轮补足

- 目标是 10 个新的 A/B 独立问题簇；
- 首轮最多派发 8 个详情任务；
- 每轮详情终态后立即执行真实性、时效、公司和问题簇选择；
- 未达到 10 条时，从剩余候选继续派发，每轮最多 4 条；
- 一次运行最多打开 24 个不同详情页；
- 达到 10 条后停止新增任务，已开始的任务正常结束并保存为候选，但本次精确交付清单只包含最终选中的 10 条；
- 达到 24 条仍不足 10 条时以 `completed_with_attention` 结束，保留全部证据并停止公开交付，绝不降低质量门槛凑数。

一个“运行”可以包含多个内部轮次，但只能产生一个 run ID、一个终态和一个精确交付清单，避免人工跨批次拼接。

## 7. 公开面经来源模块下线

“来源模块不要了”按以下边界执行：

- 删除所有公开面经 Markdown 末尾独立的 `## 来源` 区块；
- 新生成面经不得再输出 `## 来源`、原始牛客链接、A/B 等级说明或“原始记录”入口；
- 正文仍可保留不指向个人的公司、岗位、轮次和月份，这些属于面试背景而不是来源模块；
- 面经中的知识点延伸阅读链接继续保留；它们是产品知识导航，不属于采集来源模块；
- 通用知识文章自身为解释事实引用的官方参考资料不受影响；
- 原始 URL、证据等级、发布时间、内容指纹、问题簇、公开文章 key 和知识点 key 继续保存在本机原始库、候选元数据和 `.codex/interview-source-history.json`；
- 校验脚本由“公开文章必须有来源 URL”调整为“内部历史必须可追溯，公开文章不得泄露采集来源模块”。

该设计把“用户界面是否展示来源”与“系统能否核验真实性”分开：产品页面更简洁，但内部审核、去重、更新和热度统计仍有完整证据链。

## 8. 质量门槛与比较方法

### 8.1 硬门槛

新批次每篇必须满足：

- 来源在采集时不超过 30 天；
- 证据等级为 A 或 B；
- 公司属于腾讯、字节、阿里或蚂蚁；
- 主题与 Agent、RAG、MCP、AI 应用、Code Agent 或相关生产工程直接相关；
- 至少 3 个可核验技术问题；
- 正文完整，无付费截断、推广拼接或身份隐私；
- URL、内容指纹和问题簇均未形成重复公开文章；
- 所有知识点链接、树索引和构建产物有效。

任一硬门槛失败即阻止该条发布，不用长度、热度或公司覆盖进行补偿。

### 8.2 新旧统一质量评分

上一批和新一批都按同一份 100 分量表复核：

- 证据真实性与时效：25 分；
- 原始问题到文章章节的语义覆盖：20 分；
- 答案准确性、深度和失败边界：20 分；
- 知识点链接与知识库增量质量：15 分；
- 隐私、推广清理和编辑可读性：10 分；
- URL/指纹/问题簇去重及热度正确性：10 分。

合格条件是无硬门槛失败、新批平均分不低于旧批平均分，同时逐篇记录缺陷而不是只报平均值。

### 8.3 时间与资源指标

基准报告记录：

- 发现阶段耗时；
- 每轮派发数量与合格数量；
- 详情采集总耗时、P50、P90 和每分钟合格来源数；
- 编辑、知识更新、验证、推送和线上工作流耗时；
- 可恢复失败、串行兜底和永久失败数量；
- owned remote tab 峰值与结束值。

主要性能目标是相对历史 1002.7 秒活跃采集基线至少缩短 30%。若公开站点响应导致目标未达到，仍按真实数据报告，不通过增加第三个标签页或降低质量来伪造达标。

## 9. 数据与报告

每次目标补足运行保存一个不含正文的 JSON 报告，字段包括：

- run ID、计划 ID、开始/结束时间和终态；
- 每轮候选数、任务数和终态计数；
- 选中 URL 的稳定 ID、公司、证据等级、问题数和 cluster ID；
- 各阶段毫秒耗时；
- 标签页峰值与遗留数；
- 质量硬门槛结果及公开文章 key。

报告以稳定 ID 关联现有本机证据，不复制第三方正文，不进入公开网站资源。资源仓库只提交公开文章、知识点、来源历史和不含原文的质量对比报告。

## 10. 错误处理与恢复

- 扩展离线、牛客登录失效或目标补足运行超时：保持证据和运行状态，停止交付；
- 单条临时提取失败：并发轮结束后串行重试一次；
- Bridge 或扩展重启：运行依据持久任务状态协调，不重复创建已保存 URL；
- 目标不足 10 条：以需关注终态结束，不生成不完整的“成功交付”；
- 收件箱清单格式错误：保留全部条目并停止消费；
- 内容、树、历史或图片校验失败：不提交公开内容；
- Git push 或 `sync-content` 失败：保留本地提交和收件箱证据，报告 commit 与工作流错误；
- 只在公开内容确认上线后清理本轮已消费收件箱项。

## 11. 测试与验收

实现采用测试先行：

1. 调度器单测证明最多两个普通任务并发、交互任务优先、异常释放容量；
2. 扩展集成测试证明每个任务关闭自有标签、峰值不超过 2、最终无遗留；
3. 计划服务单测证明按 8 + 4 的轮次补足、达到 10 停止、24 条上限、质量不足时需关注；
4. 去重测试证明 saved/published 永久跳过、可恢复失败只重试一次、同 cluster 不重复交付；
5. 基准报告测试证明时间、质量和资源字段由真实事件计算；
6. 资源仓库测试证明公开面经没有 `## 来源` 和牛客 URL，内部来源历史仍完整且能驱动知识热度；
7. 对旧 10 篇和新 10 篇运行同一评分与结构校验；
8. 运行 Data Collector 全量测试、构建和扩展冒烟；
9. 发布资源仓库 master，等待 `sync-content` 成功并线上抽查公司样本、知识链接和来源模块下线结果。

最终交付报告必须同时给出：优化前后时间表、质量评分表、10 篇清单、知识点新增/加权清单、失败与排除原因、标签页峰值、两个仓库 commit 和线上工作流结果。
