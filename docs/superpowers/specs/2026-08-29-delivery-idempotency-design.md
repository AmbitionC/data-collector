# 投递幂等修复设计

## 问题

固定知识星球计划强制重采同一内容时，本机库会无条件把目录项的同步状态重置为
`pending`。随后计划服务按本批次的 `saved` 任务再次调用仓库收件箱 sink。正文虽然没变，
但 `collectedAt`、`batchId` 和 `contentCompletenessBuildId` 会变化，最终产生新的 Git 提交。

## 目标

- 同一内容因采集时间、批次或扩展构建变化而再次落盘时，保留已送达状态。
- 固定知识星球计划自动投递时，已送达且语义内容未变的条目不再调用目标 sink。
- 标题、正文、作者、发布时间、图片、分类、摘要或有效来源元数据变化时，仍重新投递。
- 显式人工同步保持原行为，可用于修复目标仓库丢失或重新投递。
- 不改写目标仓库已经产生的历史提交。

## 方案

为 `OrganizedDocument` 计算稳定的 `deliveryRevision`。版本覆盖收件箱真正消费的内容，
并排除 `collectedAt`、采集批次、交付批次、计划标识和完整性构建号等运行时字段。
对象键排序后再计算 SHA-256，避免属性顺序造成误判。

本机库重采时，从旧 `source.json` 计算旧版本，以兼容还没有 `deliveryRevision` 的存量目录：

- 版本相同：写入新的采集快照，但保留原 `sync` 和 `deliveryBatchId`。
- 版本不同、旧快照缺失或损坏：写入新版本，并把同步状态设为 `pending`。

`syncEntries` 增加仅供自动计划使用的 `skipDelivered` 选项。该选项开启且目录项拥有
稳定版本、目标相同并已可靠送达时，返回幂等成功但不调用 sink。知识星球固定计划开启
此选项；人工同步及牛客按交付批次的原子同步不开启。

## 验证

1. 回归测试证明只改变采集批次、构建号和采集时间时会保留同步状态。
2. 回归测试证明正文或有效元数据变化时会回到 `pending`。
3. 集成测试连续进行两轮“重采 + 自动同步”，目标 sink 只收到一次调用。
4. 全量单元/集成测试、类型检查、构建和交付冒烟全部通过后才发布。
