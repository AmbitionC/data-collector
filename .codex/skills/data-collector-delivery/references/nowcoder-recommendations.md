# 牛客产品推荐与 Skill 承接

## 目标与选帖

让有具体需要的读者开始使用 Agent Journey。热度决定有多少人可能看到，需求匹配决定是否值得参与；不以评论数、接梗能力或安装包下载量代替有效使用。

读原帖和评论后，先选择一个动作，写明对应的事实：

| 动作 | 判断依据 | 处理 |
| --- | --- | --- |
| `recommend` | 真实存在工具/资料或产品承接需求，已验证能力能直接帮助，且当前发布位置与适用版规允许产品介绍 | 给出可独立理解的实质内容；确有必要的产品说明须如实交代关系，只保留一个清楚的入口 |
| `reply_only` | 有一条实质信息、回答或必要澄清值得补充，但不需要产品入口；即使产品也有同主题资料，仍可只回答 | 说清当前问题后结束，不拼接广告；也无需为了存在感硬回 |
| `skip` | 只有娱乐热度、已有回答重复、需求已过时，或无法提供实质帮助 | 不生成回复，不用先水一条为以后引流铺垫 |

明确在对谁说：帖主、某条评论的提问者，或有同类需求的读者。楼主已挂不表示所有面经讨论都失效，但不能再对他说「面前练一轮」；应找到仍然有效的需求。对公司没名额、转正承诺落空等问题，不把面试学习工具包装成解决方案。

先判断读者是否真的需要一个产品入口，再核对能力和适用规则。面经提到“记忆”“RAG”等词，只说明题目相关，不代表对方在找资料或接受推荐。明确求资源也不自动豁免社区规则；不能据此把整条回复写成推广。无需先发几条无推广评论为营销铺垫。

需要且允许介绍入口时，按用户 2026-11-03 的最新选择使用完整裸域名 `agent-journey.cn`，不带协议或渠道参数，不仅写 `agent-journey` 让读者猜网址。描述具体用途并如实说明维护者或利益关系，不冒充独立使用者；“我在维护”不作为每帖通用开场。无需入口的评论不附域名、品牌或隐含的搜索指令。

长短按当前讨论与信息量决定，保留这个话头里值得说的一件事。把建议、产品自述、功能清单和注册要求全塞进同一条，会再次写成推广文案。对照本帖评论判断在哪儿停，不设数字字数上限，也不把所有回复压成同一结构。

## 主动求路线或资料时怎么组织

对方明确问学习路线、练习或资源，且通过上面的推荐判断时：先接住他的当前基础或卡点，在解释所需资源时简短说明自己整理或维护的具体内容，再把剩余篇幅用于他能直接执行的练习和判断方法。结尾回到这一步怎么做、遇到什么情况再补什么，不另加访问、注册或搜索指令。产品说明放在哪里取决于它与问题的关系；把同一句广告从末尾搬到中间不算改进。

例如，对已有 Java 基础、正在跟课且主动求学习路线的人，只有在本轮已读的公开路线确实包含对应分阶段练习时，才可写：

> 先别急着换老师。你问的学习路线，我在 agent-journey.cn 按阶段配了练习。你现在已经有 Java 基础，可以先给现有项目接一个工具调用，再做文档问答，参数错误、工具超时也各试一次。看看自己能不能脱离视频改需求，卡在哪里，再找讲那部分更细的课。

这是用户确认的表达方向，不是已过审样本或逐帖模板。不能把示例里的读者基础、产品内容或说话者关系挪给其他帖子；没有对应需求时，按 `reply_only` 直接回答。站内回答需要补足的内容就写在本站，不故意留半句让人离站。是否提入口与适用规则仍单独核对，不以措辞自然保证曝光、转化或免处罚。

## 社区营销规则与审核限制

2026-11-03 核对的[牛客社区规范第十五条](https://www.nowcoder.com/discuss/756927467054440448?urlSource=sitemap)区分实质干货软广和低质软广：合规类要求九成以上为有参考价值的深度分享，植入不超过一成且强相关；短、低信息密度、生硬植入的推广可能被处理。比例不是按字符拼凑即可通过的公式，也不是广告回帖或任意商业站点的通行证。个人第三方账号展示的条件不能直接当成商业网站推广授权。

普通短评优先把一个问题在站内讲清。产品说明可在符合规则、内容本身充分成立的原创文章中按需出现，不要求每篇都放。优化目标是减少无必要的推广并提高实际帮助，不是隐藏广告意图、删除域名后缀、拆字或换账号试探审核。不能用评论数、固定间隔或本机发布预算保证合规或转化。

出现新的营销警告、删评、禁言，或当前有未解除的营销审核限制时，沿用原帖、原 key/run 和证据，停止新发布；定时任务可保持启用做只读核查。验证码完成、额度到点或重连成功都不能解除这层限制；单纯讨论域名或语气也不构成解除授权。完成规范审查、用户明确确认运营方案并要求恢复后，记录这次授权和限制的解除依据，再检查当前连接、账号、验证及预算，只开始独立的新工作。这里解除的是本机运营复核状态，不宣称平台撤销处罚；实际禁言、登录失效、验证码等仍按各自流程处理。再出现新的审核事件就重新停止新操作。已有 `published + observed` 是当时观察到发送回执，不代表持续可见或平台认可；后续审核事件另记，不能抹去历史或补发被删内容。

起草审核在私有 notes 中补齐：`recommendationNeed`（原文中的真实需求）、`policyBasis`（适用规则与发布位置）、`standaloneValue`（不离站能获得什么）、`disclosure`（如有产品介绍，真实关系如何说明）、`moderationHold`（当前是否禁止发送）。这些是 Agent 判断依据，不是已实现的插件字段或自动合规认证。

## 承接渠道与能力登记

每次起草都核对产品状态，不能只凭这份文档长期认定已上线。

| 渠道 | 2026-10-29 核对结果 | 当前可用承诺 |
| --- | --- | --- |
| `site` | 已有 Agent Journey 知识与面经产品；公开知识目录 GET 核对成功，本地正文和教练工具可查 | 推荐已核实的知识内容与面经，裸域名 `agent-journey.cn`；精确能力需对应具体证据 |
| `skill` | 用户提出的对外产品方向，尚未提供或验证公开仓库、安装引用与对外鉴权 | 只作内部「上线后预演」，不产生可直接发布的已上线宣称或虚构安装命令 |
| `none` | 不需要产品承接 | `reply_only` 或 `skip`，保留原因 |

当前内部 `data-collector-delivery` Skill 用于运营者采集和交付，包含本机仓库与工作流依赖。它不是给求职者安装的产品 Skill，不能拿来当公开安装包。

本轮公开目录实际返回的内容包括 `agent-learning-roadmap`（从零到 Agent 工程师的学习路线）、`agent-open-source-contribution`（参与 Agent 开源项目与技术社区）、`react-hooks`（React 函数组件、Hooks 与状态）。分别可承接学习方向、开源入口、Hooks 代码题的具体需求；只对应内容阅读，不等于已有站外陪练能力。

未来登记对外 Skill 时至少要有：真实名称、用户任务、支持环境、已验证能力、实际安装引用、首次任务示例、账号是否必要。文案涉及的能力必须包含在已验证清单里。只给一次清楚的下一步，不把安装、注册、加群、购买同时堆进一条回复。

Skill 优先承接本来就在用兼容 Agent 工具的读者。环境未知就先确认或采用网站入口，避免为一个简单知识问题额外要求对方安装整套开发工具。

## 对外 Skill 的首版候选（方案，待产品定稿）

暂以「项目面试陪练」做样例，用户尚未确认首版任务。输入自己的项目介绍或一篇面经，连续追问具体实现、失败边界和取舍；完成一轮后输出卡住的问题、待核实的回答与复习依据。第一次就能做成一次真实练习，避免只发一长串答案、另一个万能聊天提示词或反复催注册。

本地后端已有 `search_articles`、`read_article`、`get_catalog`、学习状态工具，以及测理解、费曼和方案审稿模式，可作为能力基础。它们目前是站内教练工具，并非已验证的公共 Skill API/MCP。完整站外调用需要补产品化接口、用户鉴权、权益和调用限额；独立 Skill 也可先用用户提供材料与宿主模型完成本地练习，但不得冒称已经调用站内资料。

建议链路：牛客具体需求 → 安装匹配的 Skill → 完成一次任务 → 有同步或连续使用需求时绑定/注册 Agent Journey。安装和首次有效任务分开统计；账号绑定/注册也单独记录。历史进度同步和账号绑定是拟议增量，需实现后再宣传。Skill 自带内容一旦公开就可被读取，会员价值应依托持续更新的资料与服务能力，不把私有原始评论、凭证或整套受限内容塞进分发包。

## 在 data collector 中落地

当前即可把 `participationDecision`、`needEvidence`、`target`、`productMatch`、`destination`、`availability`、`nextAction` 写在私有起草说明里；现有台账已支持「暂不回复」。不要把主观判断说成插件已经完成评论采集或转化归因。

后续工作台按这些字段提供机会筛选和推荐依据，承接配置支持网站或 Skill；只有验证为可用的渠道才输出可发布的推荐。`planned` 的 Skill 话术独立显示为预演，不进入发布稿。不同渠道不另设固定人设、字数、比例或评论频率。

衡量首次成功完成任务、后续复用、账号绑定/注册；下载、安装和点赞只作各自阶段的信号。裸域名和普通安装引用无法天然定位具体评论，未经验证不报告逐帖转化率。

安装数只有拿到真实可观测回执时才记录，拿不到就记未知；不把仓库 star、安装器自身下载量或打开文档次数换算成产品安装与激活。
