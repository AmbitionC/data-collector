# 牛客评论调研与起草

先读真实讨论，再决定说什么。不要预设「幽默」「共情」「建议」人设，也不要沿用旧版 20–90 字、160 字上限或两句话模板。经验依据见 [nowcoder-comment-evidence.md](nowcoder-comment-evidence.md)；它是可更新的观察，不是话术库。

运营目的是让有实际需要的人发现并使用 Agent Journey。先按 [产品推荐与 Skill 承接](nowcoder-recommendations.md) 判断是否值得参与：能具体帮上忙就可以直接推荐；没有相关需求、只是适合接梗的热帖可以跳过。自然表达是执行质量，不是独立的评论数量目标。

## 起草前必须补齐的语境

1. 读完整帖文和关键配图，再读该帖推荐评论、点赞数、楼中楼及楼主后续。确认大家实际上在聊什么。标题说「上岸」可能在秀恩爱；楼主后来已挂，就不能还按等待面试结果来安慰。
2. 保存至少几个能代表当前讨论的真实评论，注明评论链接、可见赞数和观察时间。赞数只显示「点赞」时记 `null`，不是 0。没有高赞就明确说样本少，不拿别帖热评冒充本帖热评。
3. 找一个还值得接的话头：一个反差、具体疑问、遗漏的信息、真实的不满或正在延续的玩笑。先明确这句话在跟谁说，再写回复。可以问一句、补一句、接一句，也可以把一件事讲清楚，不必每次承担指导别人走出困境的角色。
4. 按本帖的对话节奏写。几字够了就结束，需要细讲就写一段；不用为了凑字数接建议、结尾总结、加表情或加域名。标点随表达自然使用，既不逐句补句号，也不机械删除所有句号。严肃长评和接梗短评都存在。
5. 对照刚读过的评论检查：有没有重复别人的整句、换几个词复述热评、接错语境、把反讽当事实、凭空断言挂面原因，或写成面向所有求职者的通用建议。反问「换个帖子还能原样贴吗」；能的话，重新找话头。

内部记录 `context / commentEvidence / participationDecision / productMatch / destination / conversationalMove / draft / caveat`。交给用户看的内容以回复本身为主，分析放在记录中。两版都必须先有参与理由，再决定切入点；不为填满草稿栏生成无关评论，也不强制按比例分配引流。判断跳过时可以不生成草稿。

## 提炼热评的方法

- 冻结热榜范围、日期和排序，再逐帖读评论。补充推荐流或热门话题时另记来源，不能把补充帖算作冻结榜单的排名。
- 记录所有实际看到的较高赞评论，优先多帖、多种场景。把同帖中的相对靠前、低赞样本作为对照，分开标记，不能一律叫高赞。不要为了凑数量降低门槛却不说明。
- 提炼「用了什么上下文 → 做了什么对话动作 → 为什么在这里成立」。同时保留长短、标点、表情和观点的反例。高赞也可能来自发布时间、曝光、复读、反讽或攻击，不能推导成唯一风格或转化效果。
- 学动作，不抄句子。热门梗可以理解其含义，但不能把一条热评改两个词当新回复，也不把网友经历挪成自己的经历。第一人称事实使用用户确认的素材。

## 证据与工具边界

正文收集继续遵守现有 `nowcoder research` 或 `nowcoder run` 的确切 run 合同。扩展当前不采集评论，`ops brief` 中 `commentsStatus: not-collected` 只表示正文资料，起草前仍需通过配置好的同一已登录浏览器读取评论。不得声称插件已采过评论。

可见评论观察独立保存为私有 study：列表快照、规范帖 URL、正文/图片语境、排序、翻过的页、每条评论原文/链接/父评论/显示赞数、观察时间、未展开或不可见内容。校验 URL 去重和覆盖计数，明确与页面总数的差额；遇登录、验证码或限制就保留进度并停，不换引擎绕过。

原始研究和试稿保存在资源库 `_inbox/_reports/nowcoder-comment-study-YYYY-MM-DD/`，不入公共面经、发布历史或 Git。仓库只保留抽象规律、少量必要短引文和原评论链接。不要把研究 study 伪装成已完成的扩展批次。

## 产品与发布

目标是让匹配的人实际使用产品，网站注册只是可选承接方式。用户正在考虑通过对外 Skill 安装和首次完成任务承接；按推荐参考中的可用性登记选择 `site / skill / none`。Skill 还在构想时，内部可写明确标为「上线后预演」的话术，实际可用稿只承诺已验证能力。推荐文案的表达按推荐参考中的当前反馈；域名只用 `agent-journey.cn` 裸域名，安装引用取真实已验证的分发信息。

起草、保存、复制均是本机准备。用户要求「拿几个帖子试试、看看生成效果」只做私有试稿；不发布、不回填虚假的评论链接、不把草稿标成已回复。
